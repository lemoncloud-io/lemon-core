# v5 B1 — Packaging (dual entry, exports, single instance)

Status: implemented and measured 2026-10-27 on `feat/v5-b1-packaging` (base `feat/v5-b0-harness`). Second bundle of the lemon-core v5 program. Gate: the B0 harness (`docs/v5/B0-local-harness.md`) plus the packaging checks below.

## Scope

- **One CommonJS build, two entries.** `require('lemon-core')` loads `dist/index.js` as before. `import 'lemon-core'` loads a generated wrapper `dist/esm/index.mjs` that re-exports the same CommonJS `module.exports`. Every global (`$engine`, the four engine modules, the Lambda handlers) exists once. No second ESM build, no `type` field, `dist/` stays where it is.
- **`exports` map** in `package.json` (`.`, `./testing`, three compatibility paths, the transition pattern `./dist/*`, `./package.json`). `main`, `types` and `files` are unchanged, so consumers with TypeScript `moduleResolution: node` see no change.
- **Engine module registration.** `$engine.register(mod)` ignores a second module with the same `getModuleName()` and logs one info line. This is the only runtime code change.
- **Docs.** `HOW_TO_UPGRADE_V5.md` (Node 24, ESM import and env order, `exports` boundary and the `./dist/*` transition, `./testing`). One line on top of `HOW_TO_UPGRADE_V4.md`.

Out of scope: a real ESM build, relative-import cleanup, `__dirname`, import-time side effects, the root default name, lemon-model re-export boundary and range, Lambda runtime.

Wrapper shape (`dist/esm/index.mjs`):

```js
// generated by scripts/gen-esm-wrapper.cjs from dist/index.d.ts. do not edit.

// ... every value name except `default`, sorted
export default cjs.default;
```

## Notes and pitfalls

1. **143 includes `default`.** The 143 value names of `etc/api-names.v4.txt` include `default`. The wrapper writes `default` as `export default cjs.default;`, so `grep -c '^export const'` is 142, and the ESM namespace has 143 keys like the CommonJS exports.
2. **ESM default import.** In ESM, `import $core from 'lemon-core'` gives `{ engine, cores, tools, controllers }`, the same object as `require('lemon-core').default`.
3. **Named ESM exports are snapshots.** `export const x = cjs.x` copies the value at load time. lemon-core does not reassign its exports, so this is the same object; do not rely on live bindings.
4. **Env order in ESM.** A static `import 'lemon-core'` runs before the importing module's code. Load env first and then `await import('lemon-core')` (`HOW_TO_UPGRADE_V5.md` § 2).
5. **`npm link` runs `prepare`.** Linking the working copy from the consumer rebuilds lemon-core (and rewrites `src/generated/field-registry.ts`). Revert that file afterwards.
6. **One stalled `npm test` run.** The first full `npm test` from a non-interactive shell stalled before collecting files (no worker process, no CPU) for 10 minutes. The cause was not found. Later runs with `< /dev/null` finished normally (about 44 s).
7. **Two installs still mean two engines.** The dedupe works within one engine. If the info line `! mod.reg(<name>) is already registered - ignored` shows up, check `npm ls lemon-core`.
