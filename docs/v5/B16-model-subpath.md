# v5 B16 — `lemon-core/model`: lemon-model through lemon-core

Status: implemented 2026-10-30 on `feat/v5-b16-model-subpath` (base `v5` @ `4c9c4e07` = 5.0.8). Decision D73 (vault). First release: the next 5.x (planned 5.0.9). User-facing changes: `HOW_TO_UPGRADE_V5.md` § 16 (and a pointer in § 10.2).

## Why

Since B4 (S-06) the lemon-core root re-exports only the 32 lemon-model names of v4. A service that needs `field`, `fieldsOf`, `specsOf` or another new lemon-model name had to declare `lemon-model` itself (`HOW_TO_UPGRADE_V5.md` § 10.2). Then each service picks its own lemon-model range, and two copies of lemon-model can end up in one install: two `CoreModel` classes, and `instanceof` across them fails. The field keys (`Symbol.for(...)`) still match, but the class identity does not.

D73: consumer repos (lemon-templates-api first, DoU later) do **not** declare `lemon-model`. They import everything from lemon-core. The lemon-core version fixes the lemon-model version ("the pair").

## Consumer rule

1. Do not put `lemon-model` in your `dependencies` or `devDependencies`.
2. The 32 v4 names (`CoreModel`, `CORE_FIELDS`, `AbstractTransformer`, `NextContext`, `NextIdentity`, `View`, `Body`, `SimpleSet`, …) come from `lemon-core`.
3. Every other lemon-model name (`field`, `fieldsOf`, `specsOf`, `FIELDS_KEY`, the 1.2–5.0 additions) comes from `lemon-core/model`.
4. `lemon-core/model` is `export * from 'lemon-model'`: the 32 root names are there too, and they are the same objects. One install holds one lemon-model, so one `CoreModel` class and one set of field keys.

```ts
import { CoreModel, NextContext } from 'lemon-core';
import { field, fieldsOf } from 'lemon-core/model';
```

## The pair pin

`dependencies.lemon-model` in lemon-core is an exact version (`5.0.2`, was `^5.0.2`). A lemon-core release names its lemon-model in `CHANGELOG.md` and in README VERSION INFO. A lemon-model change reaches services only through a lemon-core release. `npm ls lemon-model` in a service shows one copy, under lemon-core (or hoisted).

## What did not change

- The root surface. `src/cores/index.ts` and `src/index.ts` are untouched; `api:check` gives the same numbers as the base (`added=24 removed=22 not-allowed=0`).
- The S-06 boundary: `field`, `fieldsOf`, `specsOf`, `FIELDS_KEY` are still not on the root (B16 T-03).
- `lemon-core/dist/*` deep paths (until v6). `lemon-core/dist/model` also resolves now, but use `lemon-core/model`.
- Services that already declare `lemon-model` keep working. Remove the declaration when you move to the release with `./model`.

## Guard in a consumer (eslint)

```jsonc
// .eslintrc
"rules": {
    "no-restricted-imports": ["error", {
        "paths": [{ "name": "lemon-model", "message": "import from 'lemon-core' (root names) or 'lemon-core/model' (D73)." }],
        "patterns": [{ "group": ["lemon-model/*"], "message": "import from 'lemon-core/model' (D73)." }]
    }]
}
```

With `@typescript-eslint`, use `@typescript-eslint/no-restricted-imports` with the same options so `import type` is covered too.
